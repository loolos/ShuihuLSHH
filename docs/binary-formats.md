# 原版文件格式（binary-formats）

> 实现时查格式和字段就看这一份。分析方法：只读解析原版文件，并对 `ShuiHu.exe` 做静态反汇编。**没有运行原版 EXE。**解析器在 `src/formats/*.ts`。
> 置信度：**高** = 对该格式的全部文件/全部条目程序化验证通过；**中** = 结构吻合，字段语义由旁证推断；**低** = 假设，需要实验或反汇编确认。
> 下文偏移均为十六进制或十进制字节数，整数均为小端序（little-endian）。

## 1. 自定义格式的共同文件头

大多数自定义格式共用同一套头部风格：3 字节 ASCII 魔数 + 1 字节（`\0` 或版本）+ 1 字节版本号（恒为 `01`）+ u16 条目数 + u32 偏移/长度。

| 魔数（0–3） | +4 | +5 u16 | +7 | 头长 |
|---|---|---|---|---|
| `GRP\0` | `01` | 帧数 | u32 索引表偏移 | 11（后接 128 B 源路径） |
| `PIC\0` | `01` | 帧数 | u32 索引表偏移 | 11 |
| `LIB\0` | `01` | 帧数 | u16 A、u16 B、u32 C（见 §4） | 15 |
| `MAP\0` | `01` | 宽 W | u16 高 H | 9 |
| `ACT\x02` | `01` | 单位数 | u32 头长 = 11 | 11 |
| `GOO\0` | `01` | 记录数 = 200 | u32 头长 = 11 | 11 |
| `HUM\0` | `01` | 记录数 = 72 | u16 基础记录长 = 51，u32 头长 = 13 | 13 |
| `PAS` + u32 | — | — | — | 15（`+3` u32 = 文件长 − 15） |

`ShuiHu.exe` 中有 `GRP`/`grp`/`att`、`GOO`、`HUM`、`ACT`/`act`、`MAP`/`map`、`PAS`/`pab`、`GAM`（存档魔数）等短字符串，与上表一一对应（置信度：高）。

## 2. 图像帧压缩：两种 RLE

每个图像帧在索引里带 1 个编码标志，取值只有 1 和 2。按以下算法解压后，**全部 29,191 帧**的输出长度都恰好等于 宽 × 高（置信度：高）。

**编码 1 = PCX 式 RLE**

```
while 未到帧末尾:
    b = 读1字节
    if b >= 0xC0:  n = b & 0x3F; v = 读1字节; 输出 v 重复 n 次
    else:          输出 b
```

**编码 2 = PackBits（Apple/TIFF 式 RLE）**

```
while 未到帧末尾:
    n = 读1字节（视为有符号 int8）
    if 0 <= n <= 127:    原样复制接下来的 n+1 字节
    elif -127 <= n <= -1: v = 读1字节; 输出 v 重复 1-n 次
    else (n == -128):    跳过
```

两种编码都是 8 位调色板索引，按行优先排列，**无行尾标记**（行宽 = 索引里的宽度）。各库的帧四角像素几乎全为索引 0，推断**索引 0 = 透明色**（置信度：中；`Object.lib` 图标四角多为 13，是不透明的底框）。

## 3. GRP（地图图块库）与 PIC（图像库）

### 3.1 GRP 布局

```
0x00  char[4]  "GRP\0"
0x04  u8       版本 = 1
0x05  u16      帧数 N           (Grid=5, Ground=758, Upper=1018)
0x07  u32      索引表偏移        (= 最后一帧数据末尾)
0x0B  char[128] 制作时的源描述文件路径，如 "def\ground.txt"，其余补 0
0x8B  ...      帧数据（第 0 帧从 0x8B 开始）
索引表：N × 20 B
```

### 3.2 PIC 布局

与 GRP 相同，但**没有** 128 B 路径字段（第 0 帧从 0x0B 开始），且索引项为 19 B（编码标志为 u8）。

### 3.3 索引项

| 偏移 | GRP（20 B） | PIC/LIB（19 B） | 含义 | 置信度 |
|---|---|---|---|---|
| +0 | u32 | u32 | 帧数据在文件中的偏移 | 高 |
| +4 | u16 | u16 | 宽 | 高 |
| +6 | u16 | u16 | 宽的副本（全部样本都等于 +4，推测为行跨度 pitch） | 中 |
| +8 | u16 | u16 | 高 | 高 |
| +10 | s16 | s16 | 锚点 X（有符号） | 高 |
| +12 | s16 | s16 | 锚点 Y（有符号） | 高 |
| +14 | u16 | u8 | 编码：1 = PCX-RLE，2 = PackBits | 高 |
| +16 / +15 | u32 | u32 | 压缩后字节数 | 高 |

锚点证据：地表块统一为 90×46、锚点 (45, 23)，正好是菱形中心；地上物（树、房屋）锚点 Y 接近图像底部（如 84×84 → (44, 73)），符合"脚底对齐格子中心"的等距视角绘制方式。锚点是**有符号**数：`Man.lib` 有 1679 帧（39 个职业的跳跃、翻滚类动作）X 为负，如史進龍爭虎鬥第 6–26 帧从 −2 连续变到 −70 再回到 0（人物整段向一侧移动），按无符号读会变成 65 000 以上、画到屏幕外；`Upper.grp` 有 5 帧、`Effect.lib` 有 39 帧也是负值。

## 4. LIB（动画帧库）

### 4.1 布局

```
0x00  char[4] "LIB\0"
0x04  u8      版本 = 1
0x05  u16     帧数 N
0x07  u16     A          ┐ 动作组表条数 = A + B（三个文件均成立）
0x09  u16     B          ┘
0x0B  u32     C          （Effect.lib 中 C = 动作组表偏移；Man/Panel 中含义不明）
0x0F  ...     帧数据
...   动作组表：(A+B) × 8 B
EOF-19N  索引表：N × 19 B（结构同 §3.3）
```

| 文件 | N | A | B | 组表条数 | 编码 1/2 | 最大帧尺寸 |
|---|---:|---:|---:|---:|---|---|
| `Man.lib` | 26,021 | 1,620 | 72 | 1,692 | 1,033/24,988 | 186×189 |
| `Effect.lib` | 998 | 60 | 0 | 60 | 607/391 | — |
| `Panel.lib` | 112 | 73 | 34 | 107 | 29/83 | 640×480 |

### 4.2 动作组表

每项 8 B：`u16 first, u16 last, u16 count, u16 param`，全部条目满足 `count = last − first + 1`（置信度：高）。

- **`Man.lib`**：前 B = 72 项的 first/last 是**组号**范围（0–39、40–67…，合计覆盖 0–1619 共 1620 组），后 A = 1620 项的 first/last 是**帧号**范围（0–26020，连续无缺）。72 恰好等于 `Human.hum` 的职业数，因此推断为"职业 → 动作组范围 → 帧范围"的两级索引（置信度：中）。
  - 每个职业的组数都是 4 的倍数，且相邻 4 组帧数相同 → 推断每个动作含 **4 个朝向**（置信度：中）。例：职业 0（武龍）有 40 组 = 10 个动作 × 4 方向。
  - `param` 是动作类型：1 = 走路（动作 0），2 = 受击（动作 1），3 = 防御（动作 2，只有 1 帧），0 = 攻击和技能（动作 3 起，每个技能一组；士兵的动作 3 是普通攻击）。负责人看图确认（2026-11-11，武龍和士兵）；技能动作与技能表的对应顺序待逐个核对（中）。原版没有单独的站立动作，站立时用走路的第 1 帧。
- **`Effect.lib`**：60 组连续覆盖 998 帧，`param` 全为 4（用途不明；实际帧间隔由 EXE 定为 75 ms，见 §4.1）。最后 8 组各 1 帧：52–55 弓箭、56–59 飞刀，各 4 个方向。技能用哪几组见 §4.1。
- **`Panel.lib`**：107 组；包含 4 帧一组的按钮/图标状态、640×480 的全屏背景（标题画面等）。A/B 两段各自对应什么界面待确认。

### 4.1 技能特效的播放（ShuiHu.exe 静态分析，2026-11-12，置信度高，除注明者）

特效库对象在 0x448290（0x412732 载入 `data\effect.lib`）。特效对象由 0x403680 构造（+0x2f = 75 ms 计时，+0x47 = 施放者），字段：+6 组号、+8 当前帧、+0xa 格子、+0x25 技能类型、+0x27/+0x29/+0x2b = 技能子项 +6/+24/+26 各减 1、+0x2d 伤害比例、+0x31 方向、+0x3f 圈数、+0x41 范围、+0x43 形状、+0x45 段号。

| 地址 | 作用 |
|---|---|
| 0x4073e0 | 出手动画每帧：到第 k 个命中帧（子项 +28+6k）且比例非 0 时，类型不是 2 且 +6 非 0 → 0x4072e0 生成特效；否则直接结算（0x407280）。类型 8、9 在动画结束时生成一次（比例 100） |
| 0x4072e0 | 按类型选形状（跳转表 0x4073b0）：0/5/6 → 线（0x403930，形状 1）；1 → 扇（0x403980，形状 2）；2/3/4/7/8/9/11 → 菱形（0x4039e0，形状 3）；10 → 飞行（0x403a30，形状 4，从施放者格出发） |
| 0x403780 | 选组：类型 8 → 第 7 组；类型 9、11 → 第 17 组（0x11）；其余段号 0 → +6 − 1（类型 10 再加方向）、段号 1 → +24 − 1、段号 2 → +26 − 1 |
| 0x404320 | 每帧推进；`当前帧 − 本组首帧 == 触发帧表[组]`（0x4435e8，60 × s16）时调用 0x4041e0 |
| 0x4041e0 | 接力：段 0 且 +24 有值 → 同格生成段 1；段 1 且 +26 有值且该格有可作用单位（0x403b60）→ 生成段 2；否则结算该格（0x403ad0 → 0x406c60 伤害 / 0x406bd0 回复） |

## 5. MAP（战场地图）

```
0x00  char[4] "MAP\0"
0x04  u8      版本 = 1
0x05  u16     宽 W（格）
0x07  u16     高 H（格）
0x09  W×H 个格子，依次排列；每个格子是一条图层链：
        重复 { u16 tile; u8 cont; u16 flags }   // 5 B
        cont = 0 → 本格结束；cont = 2 → 后面还有一层
```

验证（置信度：高）：63 张图全部恰好解析到文件末尾（剩余 0 字节），`cont` 只出现 0 和 2。

| 观察 | 数据 | 推断 | 置信度 |
|---|---|---|---|
| 尺寸 | 18×18、36×36、54×54，`N03` 为 36×54 | 地图以 18 格为单位拼接 | 高 |
| 每格层数 | 1–5 层 | 第 1 层 = 地表，其余 = 地上物 | 中 |
| 第 1 层最大编号 | 757 | `Ground.grp` 共 758 帧（0–757），恰好吻合 | 高 |
| 后续层最大编号 | 1017 | `Upper.grp` 共 1018 帧（0–1017），恰好吻合 | 高 |
| flags（u16） | 0、0x40、0x80、0xC0 | **高度**（z）。EXE 读入时存成 flags 左移 4 位、低 4 位放 cont 的第 0 位（0x40c910），用时再右移 4 位；通行判断按高度比较（见 §5.1） | 高（用途）/ 中（是否也影响绘制未查） |
| 行列顺序 | — | 假设为行优先、等距视角下的菱形坐标；需渲染整图核对 | 低 |

`Ground.grp` 的块是 90×46 的菱形，因此地图是**等距（isometric）菱形格**；格子在屏幕上的步进（推测为 X ±45、Y ±23）尚待整图拼接验证。

### 5.1 通行判断（EXE 0x40bc30，置信度：高）

载入地图（0x409860 → 0x40bd30 → 0x40c8a0）后调用 0x40bc30：

1. 把每格每一层内存 flags 的第 0 位（阻挡位）置 1。
2. 对每格：地表图块号为 0 → 保持阻挡（图块 0 是地图外的空格，`Ground.grp` 第 0 帧是一块绿网格；重制版不画它，推测原版也不画）；查 `Ground.grp` 第 tile 帧的属性字节（由 `Ground.att` 是否 0xFF 得来，0x41f6ba；**错一位**，实际是 `att[tile − 1]`，见 §6）非 0 → 保持阻挡。
3. 没有地上物 → 清掉阻挡位（可通行）。
4. 只看**第一层**地上物：
   - 高度与地表不同：地上物高度 − 地表高度 ≥ 0x40 → 两层都清掉阻挡位（可通行，如悬在头顶的树冠）；否则保持阻挡。
   - 高度相同：查 `Upper.grp` 的属性字节（`Upper.att`）非 0 → 保持阻挡，否则清掉。

移动判定读的就是这一位（如 0x4083fe、0x40dd6c 的 `test byte [cell+2], 1`）。

寻路另建一张"层级表"（地图对象 +0x46，每格一条 10 B 节点链 {u8 可走, u8, u16 标记, u16 高度, 下一节点}，0x40c6e0 / 0x40c7c0 由图层链生成；阻挡位为 0 或被本单位占着才算可走）。寻路的单步（0x409f50 / 0x409ff0）只会落在**高度为 0** 的可走层上，且这一层上面要么没有层、要么下一层高出 ≥ 0x40；碰到高度 0 的不可走层就失败。63 张地图的地表高度全部是 0，按这个模型逐格算出的结果与上面的规则**完全一致**（0 格差异），所以单位实际上都站在地面，高度只用来让树冠、屋檐不挡路。

技能的两处高度检查也一样：0x40d7e0（施放距离沿直线扫描时，判定失败就停在这个方向）和 0x40dc80（范围内的目标）都是"最上层与地表同高，或高出 ≥ 0x40 才通过"。地表高度为 0 时永远通过，所以重制版不用实现。

相关：命令名表 VA 0x443900（移動、普通攻擊、特殊攻擊、防御、物品管理、人物資料、休息、使用、裝備、給予、丟棄…），单位命令执行 0x409690 按 unit+0x123 跳转（表 0x4097e8：0 移动 0x406000、1 攻击 0x406150、2 技能 0x406070、7 使用 0x408dc0、9 給予 0x409460，其余为空）。行动结束 0x405e80 清掉单位标志 0x4000 并把待行动计数减一；使用道具、給予都不经过它。

重制版旧规则"任一层 Upper.att = 0xFF 就阻挡"会把高出地表的树冠等也当成墙；后来又发现 .att 要错一位查（§6）。两处都改正后，N01 从起点能走到的格子由 1944 变为 2051，悬崖只挡崖边，崖上的裂土斜坡可以走；ACT 里站在阻挡格上的单位由 49 个降到 22 个（N01 为 0）。实现见 `src/rules/passability.ts`；`node tools/render-maps.ts --pass` 可以把阻挡格涂红核对。

## 6. ATT（图块属性）

```
0x00  char[4] "GPIF"（Ground.att） / "GOIF"（Upper.att）
0x04  u32     条目数 = 2048
0x08  u8[2048] 每个图块编号一个字节，取值只有 0x00 和 0xFF
```

- `Ground.att`：47 个编号为 0xFF，分布在 1–540；其余为 0。
- `Upper.att`：1962 个为 0xFF，86 个为 0。
- 用途：GRP 载入 `.att` 后把每帧的属性字节设为 `att == 0xFF`（0x41f603 起，`sete`）；通行判断怎么用见 §5.1（置信度：高）。
- **错一位**（置信度：高）：载入循环先 `add ecx, 0x10` 再从 `+0xf` 开始每 16 B 写一次（0x41f6a8–0x41f6c7），所以第 i 个字节落在第 i + 1 帧的记录里；查表 0x41f7b0 按 `基址 + tile × 16` 取记录。结果是图块 tile 用的是 `att[tile − 1]`。佐证：按错一位查，ACT 单位站在阻挡格上的数量从 49 降到 22，N01 的裂土斜坡也变成可走。注意地上物只在与地表同高时才看这个值。

## 7. ACT（关卡单位配置）

**区块**：u16 长度，再加 7 个 u16 头字 w0..w6（w0 = 1 普通，4/5 带区域条件），然后是条件树（区块 +16 起），条件树之后是指令。代码里的 w7、w8 就是根节点的 n 和 A（叶子类型）。

**条件树**（0x411410 求值，高）：每个节点 {u16 n, u16 A, u16 B, u16 comb}，后接 n 字节参数（n = 2 一个 u16，n = 4 两个）。

- A = 0xFF：左边是子节点；B = 0xFF：右边是子节点；B = 0xFFFF：只有一个叶子 A。
- comb 0 = 或，1 = 且。
- 按这个结构解析，300 个区块的指令起点全部对齐。

## 12. 其它格式

- **`Default.pal`**：768 B = 256 × (R, G, B)，每通道 0–255（不是 VGA 的 0–63）。索引 0 = 黑 (0,0,0)。（高）
- **`Default.tbl`**：65,536 B = 256 × 256 u8，满足 `tbl[a][b] = tbl[b][a]`，推断为两种调色板颜色混合（半透明/阴影）后的查找表。与 50% 平均色的平均偏差约 34/255，混合公式未定。（结构高，公式低）
- **`Stdfont.16f` / `Stdfont.24f`**：13,973 字 × 32 B（16×16，1bpp，每行 2 字节，高位在左）/ × 72 B（24×24）。字序 = Big5 码位 `(hi − 0xA1) × 157 + (lo < 0x7F ? lo − 0x40 : lo − 0xA1 + 63)`。（高）
- **`Title\*.flc`**：标准 FLC，ffmpeg 可直接解码。（高）
- **`Sound\*.wav`**：标准 PCM；226 个为 22,050 Hz/16 bit/立体声，其余为 11,025/22,050/44,100 Hz 的单声道或 8 bit。（高）
- **`music.ini`**：141 行 `编号=值`，值 2–24 或空；推测为"场景/事件 → CD 音轨号"（低）。
- **`game.ini`**：`SCROLLSPEED/SOUND/MIDI/VOICE/VIEWENEMY/SAVE`，与 EXE 中的键名字符串一致。
